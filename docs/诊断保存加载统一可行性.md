## 3. 项目关联资料 → 项目根 映射（核心）

### 3.1 报告工作台"项目关联资料"存哪

`ui/report_workbench.py:109,132,224,391-394`：


**格式**: 全是绝对路径字符串，如 `D:/监测数据/2026/.../something.txt` 或 `项目资料库/三组标定/数据/something.csv`。

### 3.2 已有可靠的"项目根"反推逻辑

报告生成已在用 (`main.py:1234-1248`)，可完全复用：

```python
# main.py:1237-1244 — 从关联资料反推项目根
_KNOWN_SUB = {'数据', '方案', '图纸', '图片', '视频', '其它', '报告'}
all_files = [f for f in [req_file] + project_files if f]
if all_files:
    base_dirs = {os.path.dirname(os.path.abspath(f)) for f in all_files}
    candidate = os.path.commonpath(list(base_dirs)) if len(base_dirs) > 1 else base_dirs.pop()
    # 若落在项目子文件夹内 → 上提一级到项目根
    if os.path.basename(candidate) in _KNOWN_SUB:
        candidate = os.path.dirname(candidate)
    report_dir = os.path.join(candidate, '报告')
```

**算法**：
1. 取所有关联文件路径 → `os.path.dirname` → 公共父目录
2. 若公共父目录的 basename 是已知子文件夹（`数据`/`报告`/`图片` 等）→ 上提一级
3. 结果即项目根目录

### 3.3 项目根的识别标志

当前系统没有显式项目标识文件（如 `project.json` 或 `.project`）。识别靠**目录层级结构约定**：

```
项目资料库/
├── 三组标定/          ← 项目根 (不是 _KNOWN_SUB)
│   ├── 数据/          ← _KNOWN_SUB
│   │   └── 诊断记录/  ← 目标
│   ├── 图片/
│   └── 报告/
├── 应变传感器标定/
│   └── ...
```

"上提一级到不在 _KNOWN_SUB"的反推逻辑，**不依赖显式标识文件，靠路径结构**。这能工作但不如显式标识稳健——如果用户添加的文件直接就在项目根（如 `项目资料库/三组标定/readme.txt`），`commonpath` 就是项目根本身，不需上提。

### 3.4 更好的选择：复用保存对话框的"已选项目"

`_save_diagnosis_to_project` (`ai_diagnosis.py:1237-1289`) 已让用户在**保存时选项目**。这个信息可以直接复用给加载：

- 保存侧：`sel` (用户选的项目名) + `proj_dir` (项目资料库) → `target = 项目资料库/{sel}`
- 加载侧：把 `_handle_load_diagnosis` 改为同样逻辑——**先让用户选项目 → 再扫该项目的 `数据/诊断记录/`**

但 `_handle_load_diagnosis` 当前无"选项目"UI，只有"选文件"UI。需加一步（或从关联资料反推，跳过选项目步骤）。

**两套方案比较**：

| 方案 | 逻辑 | 复杂度 | 依赖 |
|------|------|--------|------|
| A — 关联资料反推项目 | 从 `report_workbench._proj_file_list` 取路径 → `commonpath` → 上提 → 扫 `数据/诊断记录/` | 低 — 99% 逻辑已有 | 用户需先在报告工作台添加过文件 |
| B — 显式选项目 | 加载时弹选定项目对话框（复用 `_save_diagnosis_to_project` 的项目列表 UI）→ 扫选中项目的 `数据/诊断记录/` | 中 — 需加项目选择步骤 | 无 |

## 4. 边界情况

### 4.1 关联资料为空（没添加文件）

`main.py:1239` 的兜底逻辑：

```python
if all_files:
    candidate = ...
else:
    report_dir = os.path.join(BASE_DIR, '报告')  # 兜底: 软件根/报告
```

**方案 A** 下：关联资料为空 → `_handle_load_diagnosis` 无法反推项目 → 弹窗提示"请先在报告工作台添加项目关联资料"；或降级到方案 B（显式选项目）。

**方案 B** 下：不需要关联资料，用户直接从项目列表选。

### 4.2 关联资料混了多个项目的文件

`main.py:1240-1241`：

```python
base_dirs = {os.path.dirname(os.path.abspath(f)) for f in all_files}
candidate = os.path.commonpath(list(base_dirs)) if len(base_dirs) > 1 else base_dirs.pop()
```

`os.path.commonpath` — 若多个项目路径无公共父目录（如 `D:/项目A/` 和 `E:/项目B/`），抛 `ValueError`。若在同一个项目资料库下（如 `资料库/A/数据/` 和 `资料库/B/报告/`），commonpath 退回资料库根 → `_KNOWN_SUB` 不认识 → 不以子文件夹名匹配 → candidate = 资料库根（不对）。

**处理**: 检测多项目混合 → 弹提示"关联资料涉及多个项目，请先统一到一个项目"。或者在加载 UI 中多加一步选项目，忽略反推。

### 4.3 保存对话框的"已选项目"能否复用

`_save_diagnosis_to_project` 中 `sel` 变量仅在 `on_ok()` 闭包内有效，传入 `target` 构造目录后即销毁。`_handle_load_diagnosis` 拿不到它。

但**项目列表源是同一个**: `getattr(main_win, 'get_project_library_dir', lambda: '')()`。加载也可以扫 `项目资料库/` 下列出子文件夹，让用户先选项目 → 再扫 `数据/诊断记录/` → 列出记录。

### 4.4 加载 UI 当前已有两层选择（项目 → 记录列表）

当前加载 UI (`main.py:1119-1161`) 只有一层（`QListWidget` 列文件）。改成两层：
1. 第一层：选项目（扫 `项目资料库/` 下子目录）
2. 第二层：选记录（扫 `项目资料库/{项目}/数据/诊断记录/*.json`）

复杂度不高，`_build_diagnosis_record` 的模式已有类似 UI。

## 5. 旧记录兼容

### 5.1 旧记录分两处

| 位置 | 文件名 | 数量 |
|------|--------|------|
| `wiki_vault/diagnoses/` | `AI诊断_20260620_*.json` | 3 份 |
| `项目资料库/三组标定/数据/` | `诊断记录_20260626_*.json` | 本次新存 |

### 5.2 统一后旧记录能否加载

**`wiki_vault/diagnoses/` 中的旧记录**: 不在 `数据/诊断记录/` 下 → 扫不到 → 加载列表不出现。除非：

- **兼容扫描**: 保留 `wiki_vault/diagnoses/` 作为 fallback（当项目路径下无诊断记录时扫旧目录）
- **迁移**: 手动复制 JSON 到新位置
- **不兼容**: 接受旧记录需手动迁移，提示文案告知

**`项目资料库/三组标定/数据/` 中的新记录**: 改名/移动——`诊断记录_*.json` 目前在 `数据/` 下，需移到 `数据/诊断记录/`。否则同样扫不到。

### 5.3 建议兼容策略

`list_diagnoses` 双源扫描（按优先级）：
1. 先扫 `{项目根}/数据/诊断记录/*.json` — 主力
2. 若为空，降级扫 `wiki_vault/diagnoses/*.json` — 兼容旧记录

这样旧记录不会丢失，新记录优先出现。`read_diagnosis` 调 `diag_dir / f"{name}.json"` 时 `name` 来自 scan 结果的 `f.stem`，路径已包含目录信息 → 读取路径正确。
